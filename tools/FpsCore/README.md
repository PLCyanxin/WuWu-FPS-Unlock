# FPS 核心源码候选

此目录包含内置 FPS 核心的独立重构候选。它已整合进本地 v1.2.2RC 测试包，尚未通过游戏实测。`SOURCE.json` 固定了上游源码提交与原 DLL 的来源哈希；`LICENSE` 保留了上游 MIT 许可证。

候选保留了原管道名称、六字段消息、154 字节标记、按地址升序选择首标记的顺序，以及从后续 `0x70` 标记向前 4 KiB 寻找第二个 FPS 浮点候选的规则。它没有增加高级功能，也没有新增游戏钩子。

候选修复了以下问题：

- 原实现可能把多轮扫描中的同一个地址计为两个候选。候选每轮重新计数，只有本轮找到两个不同地址才继续。
- 原搜索在范围小于签名时可能发生无符号下溢。候选先检查长度，并在找到首标记后停止扫描。
- 原 FPS 全局变量存在跨线程非原子访问。候选使用原子整数，并在收到第一条有效指令前保持不写入。
- 候选严格校验六个字段及完整消息，接受 30–420 FPS；它拒绝非数值、溢出、尾随内容和超长消息。其他五个字段仍然不控制任何功能。
- 候选在一次 4 KiB 搜索未找到目标后等待 51ms，最长等待时间仍为 915 秒。它不再持续忙等。
- 候选仍每 51ms 检查一次目标，仅在目标值不同于请求时写入。它不会降低检查频率来换取较少唤醒。

扫描不再分配全进程区域列表或全部匹配列表。签名保留交错表示，扫描跳过自身模块，避免命中自身保存的签名。扫描以重叠块检查，并保留异常保护；并发失效的内存块可能被跳过，不能把这一行为宣称为任何运行态布局都完全等价。

候选只在主程序文件名为 `Client-Win64-Shipping.exe` 时初始化。工作线程开始长期工作前固定自身模块，成功后不支持热卸载。调用方不得在初始化线程开始之前卸载它。`RequestFpsCoreStop` 只发出停止请求；当前启动器没有调用此新增入口，也没有新增管道停止协议。停止事件保留至进程结束，`DllMain` 不等待线程。

管道使用可取消的重叠 I/O，取消完成后才关闭句柄。它拒绝远程连接，但保留 Windows 默认 DACL，未提供本地客户端身份认证。现有管道没有应用结果回执，因此连接成功与发送成功均不能证明游戏帧率已改变。

可以在 Windows x64 的 MSVC 开发环境执行以下命令构建候选并运行隔离测试：

```powershell
./tools/FpsCore/Build.ps1 -OutputDirectory ./artifacts/tests/fps-core-candidate
```

输出文件名为 `ww_fps_core_candidate.dll`。脚本不会复制它到现有组件目录或游戏目录。测试程序使用自己创建的内存和独立管道，不加载该 DLL，不执行生产扫描，也不启动或访问游戏进程。测试涵盖协议、并发请求、重复候选、首匹配、必要写入与阻塞管道取消。扫描基准只比较相同测试数据上的算法工作量，不代表游戏启动时间或游戏 FPS 收益。
